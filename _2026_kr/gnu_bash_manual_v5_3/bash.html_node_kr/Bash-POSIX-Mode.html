6.11.1 POSIX란 무엇인가? ¶

POSIX는 유닉스(Unix)에 기반한 표준 패밀리의 이름입니다. 기본적인 시스템 콜(system calls)과 C 라이브러리 함수부터 일반적인 애플리케이션과 도구, 그리고 시스템 관리 및 관리에 이르기까지 다양한 유닉스 서비스, 도구, 함수들이 이 표준의 일부입니다.

POSIX 쉘 및 유틸리티(Shell and Utilities) 표준은 원래 IEEE Working Group 1003.2 (POSIX.2)에 의해 개발되었습니다. 1003.2 표준의 첫 번째 판은 1992년에 출판되었습니다. 이후 원래의 IEEE 1003.1 워킹 그룹과 합쳐졌으며, 현재는 Austin Group (IEEE, The Open Group, ISO/IEC SC22/WG15의 공동 워킹 그룹)에 의해 유지 관리되고 있습니다. 오늘날 쉘 및 유틸리티는 IEEE Std 1003.1-2024를 구성하는 문서 세트 내의 한 권(volume)이며, 따라서 과거의 POSIX.2(1992년 판)는 현재의 통합 POSIX 표준의 일부입니다.

쉘 및 유틸리티 권은 명령 해석기(command interpreter) 인터페이스와 명령줄 또는 다른 프로그램에 의해 흔히 실행되는 유틸리티 프로그램들에 집중합니다. 이 표준은 웹에서 자유롭게 확인할 수 있습니다: https://pubs.opengroup.org/onlinepubs/9799919799/utilities/contents.html.

Bash는 POSIX 쉘 및 유틸리티 권에서 정의된 쉘 동작의 측면들과 관련이 있습니다. 쉘 명령어 언어는 물론 표준화되었으며, 여기에는 기본적인 흐름 제어 및 프로그램 실행 구조, I/O 리다이렉션 및 파이프라인, 인자 처리, 변수 확장, 그리고 인용(quoting)이 포함됩니다.

원하는 기능을 제공하기 위해 쉘의 일부로 구현되어야 하는 특수(special) 빌트인들이 쉘의 일부로 명시되어 있습니다; eval과 export가 그 예입니다. 쉘에만 전념하지 않는 POSIX의 다른 섹션들에도 흔히 빌트인 명령어로 구현되는(어떤 경우에는 반드시 구현되어야 하는) 유틸리티들이 나타나는데, read와 test가 그러한 예입니다. POSIX는 또한 작업 제어(job control)와 명령줄 편집을 포함한 쉘의 대화형 동작 측면도 명시합니다. 오직 vi 스타일의 라인 편집 명령어들만 표준화되었습니다; emacs 편집 명령어들은 반대 의견으로 인해 제외되었습니다.

6.11.2 Bash POSIX 모드 ¶

Bash는 POSIX 쉘 사양의 구현체이지만, Bash의 기본 동작이 사양과 다른 부분들이 있습니다. Bash posix 모드는 이러한 부분에서 Bash의 동작을 변경하여 표준을 더 엄격하게 준수하도록 만듭니다.

--posix 명령줄 옵션과 함께 Bash를 시작하거나, Bash가 실행 중일 때 ‘set -o posix’를 실행하면, Bash의 기본값이 다른 영역에서 POSIX에 명시된 대로 동작을 변경함으로써 POSIX 표준에 더 가깝게 부합하게 됩니다.

sh라는 이름으로 호출되었을 때, Bash는 시작 파일들을 읽은 후 POSIX 모드로 진입합니다.

다음은 POSIX 모드가 활성화되었을 때 변경되는 사항들의 목록입니다:

  1. Bash는 POSIXLY_CORRECT 변수가 설정되도록 보장합니다.
  2. Bash는 일반적인 Bash 파일 대신 POSIX 시작 파일($ENV)을 읽고 실행합니다(Bash 시작 파일 참조).
  3. 비대화형 쉘에서도 별칭 확장(alias expansion)이 항상 활성화됩니다.
  4. 예약어(reserved words)가 인식되는 컨텍스트에서 나타나는 예약어들은 별칭 확장의 대상이 되지 않습니다.
  5. 명령어 치환(command substitution)을 처음 파싱할 때 별칭 확장이 수행됩니다. 기본(비-posix) 모드에서는 보통 별칭 확장이 활성화되어 있더라도 명령어 치환이 실행될 때까지 지연시킵니다. 이는 명령어 치환이 처음 파싱된 이후에 정의된 별칭(예: 함수의 일부로 정의됨)은 명령어 치환에서 확장되지 않음을 의미합니다.
  6. time 예약어를 단독으로 단순 명령어로 사용할 수 있습니다. 이 방식으로 사용되면 쉘과 종료된 자식 프로세스들에 대한 시간 통계를 표시합니다. TIMEFORMAT 변수가 시간 정보의 형식을 제어합니다.
  7. 다음 토큰이 ‘-’로 시작하면 파서는 time을 예약어로 인식하지 않습니다.
  8. 큰따옴표 내에 나타나는 ${…} 확장을 파싱하고 확장할 때, 연산자가 패턴 제거를 수행하도록 정의된 것들 중 하나가 아닌 한, 작은따옴표는 더 이상 특별하게 취급되지 않으며 닫는 중괄호나 다른 특수 문자를 인용하는 데 사용될 수 없습니다. 패턴 제거 연산자인 경우, 작은따옴표들이 반드시 쌍으로 나타날 필요는 없습니다.
  9. 대화형 쉘이 아닌 한, 리다이렉션 연산자는 리다이렉션 대상 단어에 대해 파일 이름 확장(filename expansion)을 수행하지 않습니다.
  10. 리다이렉션 연산자는 리다이렉션 대상 단어에 대해 단어 분할(word splitting)을 수행하지 않습니다.
  11. 함수 이름은 POSIX 특수 빌트인 중 하나와 같을 수 없습니다.
  12. 물결표 확장(tilde expansion)은 줄의 모든 할당문이 아니라, 명령어 이름 앞에 오는 할당문들에 대해서만 수행됩니다.
  13. 변수 간접 참조(variable indirection)가 가능하지만, ‘#’ 및 ‘?’ 특수 파라미터에는 적용할 수 없습니다.
  14. 확장이 큰따옴표로 감싸진 패턴 컨텍스트에서 ‘*’ 특수 파라미터를 확장할 때, $*를 큰따옴표로 감싸진 것처럼 취급하지 않습니다.
  15. 확장을 거치는 히어 도큐먼트(here-document) 본체 내의 백틱(` `) 명령어 치환에 큰따옴표 문자(‘"’)가 나타나면 특별하게 취급됩니다. 이는 예를 들어 큰따옴표 앞에 오는 백슬래시가 큰따옴표를 이스케이프하며 백슬래시는 제거됨을 의미합니다.
  16. 명령어 치환은 ‘?’ 특수 파라미터를 설정하지 않습니다. 명령어 단어가 없는 단순 명령어의 종료 상태는 여전히 해당 명령어의 변수 할당 및 리다이렉션을 평가하는 동안 발생한 마지막 명령어 치환의 종료 상태이지만, 이는 모든 할당과 리다이렉션이 끝난 후에야 발생합니다.
  17. PATH 변수 요소의 첫 번째 문자로 나타나는 리터럴 물결표는 위 물결표 확장에서 설명한 대로 확장되지 않습니다.
  18. 명령어 검색 시 type 및 command 빌트인에 의해 출력되는 내용을 포함하여, 쉘 함수보다 POSIX 특수 빌트인을 먼저 찾습니다.
  19. 슬래시를 포함한 이름을 가진 쉘 함수가 POSIX 모드 진입 전에 정의되었더라도, 쉘은 이름에 하나 이상의 슬래시가 포함된 함수를 실행하지 않습니다.
  20. 해시 테이블(hash table)에 있는 명령어가 더 이상 존재하지 않을 때, Bash는 새로운 위치를 찾기 위해 $PATH를 다시 검색합니다. 이는 ‘shopt -s checkhash’로도 사용 가능합니다.
  21. Bash는 실행 비트(execute bit)가 설정되지 않은 명령어를 $PATH 검색의 (최후의) 결과로 반환하더라도 명령어 해시 테이블에 삽입하지 않습니다.
  22. 작업 제어(job control) 코드와 빌트인이 작업이 0이 아닌 상태로 종료될 때 출력하는 메시지는 ‘Done(status)’입니다.
  23. 작업 제어 코드와 빌트인이 작업이 중단되었을 때 출력하는 메시지는 ‘Stopped(signame)’입니다 (예: signame은 SIGTSTP).
  24. 대화형 쉘인 경우, Bash는 ‘;’ 또는 줄바꿈으로 구분된 목록 내의 명령어들을 실행하는 도중에는 작업 알림(job notifications)을 수행하지 않습니다. 비대화형 쉘은 목록 내의 포그라운드 작업이 완료된 후 상태 메시지를 출력합니다.
  25. 대화형 쉘인 경우, Bash는 상태가 변경된 백그라운드 작업이나 시그널로 인해 종료된 포그라운드 작업의 상태를 출력하기 전에 다음 프롬프트가 뜰 때까지 기다립니다. 비대화형 쉘은 포그라운드 작업이 완료된 후 상태 메시지를 출력합니다.
  26. Bash는 wait 또는 jobs 빌트인을 통해 사용자에게 종료 사실을 알린 후 작업 테이블에서 작업을 영구히 제거합니다. 사용자에게 종료를 알린 후 작업 목록에서 해당 작업을 제거하지만, wait에 PID 인자가 제공되는 한 상태 정보는 여전히 wait을 통해 확인 가능합니다.
  27. vi 편집 모드에서 ‘v’ 명령이 실행될 때, $VISUAL 및 $EDITOR를 확인하는 대신 vi 에디터를 직접 호출합니다.
  28. 프롬프트 확장은 ‘!’를 히스토리 번호로, ‘!!’를 ‘!’로 바꾸는 POSIX PS1 및 PS2 확장을 활성화하며, Bash는 promptvars 옵션 설정과 관계없이 PS1 및 PS2 값에 대해 파라미터 확장을 수행합니다.
  29. 기본 히스토리 파일은 ~/.sh_history입니다 (이는 쉘이 $HISTFILE에 할당하는 기본값입니다).
  30. histexpand 옵션이 활성화되어 있더라도, 큰따옴표로 감싸진 문자열 내의 ‘!’ 문자는 히스토리 확장을 시작하지 않습니다.
  31. 쉘 함수 정의를 출력할 때(예: type에 의해), Bash는 꼭 필요한 경우가 아니면 function 예약어를 출력하지 않습니다.
  32. 비대화형 쉘은 산술 확장(arithmetic expansion)의 문법 오류로 인해 유효하지 않은 식이 생성될 경우 종료됩니다.
  33. 비대화형 쉘은 파라미터 확장 에러가 발생하면 종료됩니다.
  34. POSIX 특수 빌트인이 에러 상태를 반환하면 비대화형 쉘은 종료됩니다. 치명적인 에러들은 POSIX 표준에 나열된 것들이며, 잘못된 옵션 전달, 리다이렉션 에러, 명령어 이름 앞의 변수 할당 에러 등이 포함됩니다.
  35. 할당문 뒤에 명령어 이름이 오지 않을 때 변수 할당 에러가 발생하면 비대화형 쉘은 에러 상태로 종료됩니다. 변수 할당 에러는 예를 들어 읽기 전용(readonly) 변수에 값을 할당하려고 할 때 발생합니다.
  36. 특수 빌트인 앞의 할당문에서 변수 할당 에러가 발생하면 비대화형 쉘은 에러 상태로 종료되지만, 다른 단순 명령어의 경우에는 그렇지 않습니다. 다른 단순 명령어의 경우 쉘은 해당 명령어의 실행을 중단하고 최상위 레벨에서 실행을 계속합니다("쉘은 에러가 발생한 명령어에 대해 더 이상의 처리를 수행하지 않아야 함").
  37. for 문의 반복 변수나 select 문의 선택 변수가 읽기 전용 변수이거나 유효하지 않은 이름인 경우, 비대화형 쉘은 에러 상태로 종료됩니다.
  38. . filename 에서 filename을 찾을 수 없으면 비대화형 쉘은 종료됩니다.
  39. . 이나 source 빌트인으로 읽어들인 스크립트에 문법 오류가 있거나, eval 빌트인에 의해 처리되는 문자열에 문법 오류가 있으면 비대화형 쉘은 종료됩니다.
  40. export, readonly, 또는 unset 빌트인 명령어가 유효한 식별자가 아닌 인자를 받았고 쉘 함수에 작용하는 것이 아니라면, 비대화형 쉘은 종료됩니다. 이들은 특수 빌트인이기 때문에 이러한 에러는 종료를 강제합니다.
  41. POSIX 특수 빌트인 앞에 오는 할당문은 빌트인이 완료된 후에도 쉘 환경에 유지됩니다.
  42. command 빌트인은 할당문을 인자로 받는 빌트인들이 할당문으로서 확장하는 것을 막지 않습니다; POSIX 모드가 아닐 때 선언 명령어들은 command 뒤에 올 경우 할당문 확장 특성을 잃게 됩니다.
  43. POSIX 모드를 활성화하면 inherit_errexit 옵션이 설정되는 효과가 있어, 명령어 치환을 실행하기 위해 생성된 서브쉘은 부모 쉘로부터 -e 옵션 값을 상속받습니다. inherit_errexit 옵션이 활성화되지 않았을 때 Bash는 그러한 서브쉘에서 -e 옵션을 해제합니다.
  44. POSIX 모드를 활성화하면 shift_verbose 옵션이 설정되는 효과가 있어, shift에 전달된 숫자 인자가 위치 파라미터의 개수를 초과하면 에러 메시지가 출력됩니다.
  45. POSIX 모드를 활성화하면 interactive_comments 옵션이 설정되는 효과가 있습니다(주석 참조).
  46. . 및 source 빌트인은 PATH 검색을 통해 파일 이름을 찾지 못한 경우 현재 디렉토리에서 찾으려 하지 않습니다.
  47. alias 빌트인이 별칭 정의를 표시할 때, -p 옵션이 제공되지 않는 한 앞에 ‘alias ’를 붙여 표시하지 않습니다.
  48. bg 빌트인은 백그라운드로 보내진 각 작업을 설명하기 위해 필수 형식을 사용하며, 여기에는 해당 작업이 현재 작업인지 이전 작업인지에 대한 표시가 포함되지 않습니다.
  49. cd 빌트인이 논리(logical) 모드로 호출되었을 때, $PWD와 인자로 제공된 디렉토리 이름으로 구성된 경로명이 실존하는 디렉토리를 참조하지 않는다면, 물리(physical) 모드로 대체하지 않고 실패합니다.
  50. $PWD와 인자로 제공된 디렉토리 이름으로 구성된 경로명의 길이가 정규화(canonicalized)되었을 때 PATH_MAX를 초과하여 cd 빌트인이 디렉토리를 변경할 수 없는 경우, cd는 제공된 디렉토리 이름을 그대로 사용하려고 시도합니다.
  51. xpg_echo 옵션이 활성화되었을 때, Bash는 echo의 그 어떤 인자도 옵션으로 해석하려 하지 않습니다. echo는 각 인자의 이스케이프 시퀀스를 변환한 후 표시합니다.
  52. export 및 readonly 빌트인 명령어는 POSIX가 요구하는 형식으로 출력을 표시합니다.
  53. 히스토리를 나열할 때, fc 빌트인은 히스토리 항목의 수정 여부를 표시하지 않습니다.
  54. fc가 사용하는 기본 에디터는 ed입니다.
  55. fc는 추가적인 인자들을 무시하지 않고 에러로 처리합니다.
  56. fc -s에 너무 많은 인자가 제공되면 fc는 에러 메시지를 출력하고 실패를 반환합니다.
  57. ‘kill -l’의 출력은 모든 시그널 이름을 ‘SIG’ 접두사 없이 공백으로 구분하여 한 줄에 출력합니다.
  58. kill 빌트인은 ‘SIG’ 접두사가 붙은 시그널 이름을 허용하지 않습니다.
  59. kill 빌트인은 pid나 작업 인자 중 하나라도 유효하지 않거나, 그 중 하나에라도 지정된 시그널을 보내는 데 실패하면 실패 상태를 반환합니다. 기본 모드에서 kill은 지정된 프로세스들 중 하나라도 시그널 전송에 성공하면 성공을 반환합니다.
  60. printf 빌트인은 부동 소수점 변환 지정자에 대응하는 인자들을 변환할 때, 사용 가능하더라도 long double 대신 (strtod를 통해) double을 사용합니다. ‘L’ 길이 수정자를 사용하면 printf가 사용 가능한 경우 long double을 사용하도록 강제할 수 있습니다.
  61. pwd 빌트인은 -P 옵션을 통해 파일 시스템 확인을 요청받지 않았더라도, 자신이 출력하는 값이 현재 디렉토리와 동일한지 검증합니다.
  62. read 빌트인은 트랩이 설정된 시그널에 의해 중단될 수 있습니다. Bash가 read 실행 중에 트랩된 시그널을 받으면 트랩 핸들러가 실행되고 read는 128보다 큰 종료 상태를 반환합니다.
  63. 옵션 없이 set 빌트인이 호출될 때, 쉘 함수 이름과 정의를 표시하지 않습니다.
  64. 옵션 없이 set 빌트인이 호출될 때, 변수 값에 쉘 메타 문자가 포함되어 있지 않다면 (출력 불가능한 문자가 포함되어 있더라도) 따옴표 없이 값을 표시합니다.
  65. test 빌트인은 ‘<’ 및 ‘>’ 이항 연산자를 평가할 때 현재 로케일을 사용하여 문자열을 비교합니다.
  66. test 빌트인의 -t 단항 기본 요소는 인자를 요구합니다. 과거 버전의 test는 특정 경우에 인자를 선택 사항으로 만들었으며, Bash는 하위 호환성을 위해 이를 수용하려고 시도합니다.
  67. trap 빌트인은 시작 부분의 SIG 없이 시그널 이름을 표시합니다.
  68. trap 빌트인은 첫 번째 인자가 오직 숫자로만 구성된 유효한 시그널 번호가 아닌 한, 해당 인자가 시그널 사양일 가능성을 확인하여 시그널 처리를 원래의 배치(disposition)로 되돌리지 않습니다. 사용자가 특정 시그널의 핸들러를 원래 배치로 리셋하고 싶다면 첫 번째 인자로 ‘-’를 사용해야 합니다.
  69. 인자 없는 trap -p는 트랩된 시그널뿐만 아니라, 배치가 SIG_DFL로 설정된 시그널들과 쉘 시작 시 무시되었던 시그널들도 표시합니다.
  70. type 및 command 빌트인은 실행 가능하지 않은 파일을 발견된 것으로 보고하지 않지만, 해당 이름의 파일이 $PATH에서 유일하게 발견된 것이라면 쉘은 그 파일을 실행하려고 시도합니다.
  71. ulimit 빌트인은 -c 및 -f 옵션에 대해 512바이트의 블록 크기를 사용합니다.
  72. unset 빌트인에 -v 옵션이 지정되었을 때 readonly 또는 해제 불가능한 변수를 해제하려고 시도하면 치명적인 에러를 반환하며, 이로 인해 비대화형 쉘은 종료됩니다.
  73. 명령어 앞에 오는 할당문에 나타나는 변수를 해제하도록 요청받았을 때, unset 빌트인은 현재 또는 이전 범위에 있는 동일한 이름의 변수 또한 해제하려고 시도합니다. 이는 "할당된 변수가 유틸리티에 의해 더 수정된다면, 유틸리티에 의해 행해진 수정 사항이 유지되어야 함"이라는 요구 사항을 구현한 것입니다.
  74. SIGCHLD에 트랩이 설정되어 있을 때 SIGCHLD가 도착하더라도 wait 빌트인을 중단시키고 즉시 반환하게 만들지 않습니다. 트랩 명령어는 종료된 각 자식 프로세스에 대해 한 번씩 실행됩니다.
  75. Bash는 wait 빌트인이 종료된 백그라운드 프로세스의 상태를 반환한 후 해당 상태를 상태 목록에서 제거합니다.

POSIX 모드일 때라도 Bash가 기본적으로 구현하지 않는 추가적인 POSIX 동작들이 있습니다. 구체적으로는 다음과 같습니다:

  1. POSIX는 단어 분할(word splitting)이 바이트 지향적(byte-oriented)일 것을 요구합니다. 즉, IFS 값의 각 바이트가 잠재적으로 단어를 분할하며, 이는 해당 바이트가 IFS 내의 다중 바이트 문자의 일부이거나 단어 내의 다중 바이트 문자의 일부일 때도 마찬가지입니다. Bash는 IFS 값에 다중 바이트 문자를 허용하며, 유효한 다중 바이트 문자를 단일 구분자로 취급하고, 해당 문자를 구성하는 바이트 중 하나가 IFS에 나타나더라도 유효한 다중 바이트 문자를 분할하지 않습니다. 이는 POSIX 해석 1560이며, 이슈 1924에 의해 추가로 수정되었습니다.
  2. fc 빌트인은 FCEDIT이 설정되어 있지 않을 때 직접 ed를 기본값으로 사용하는 대신, 히스토리 항목을 편집할 프로그램으로 $EDITOR를 확인합니다. Bash는 EDITOR도 설정되어 있지 않은 경우에만 ed를 사용합니다.
  3. 위에서 언급했듯이, Bash는 echo 빌트인이 완전히 호환되도록 하기 위해 xpg_echo 옵션이 활성화될 것을 요구합니다.

Bash를 빌드할 때 configure에 --enable-strict-posix-default를 지정함으로써 기본적으로 POSIX 준수 상태가 되도록 구성할 수 있습니다(선택적 기능 참조).
