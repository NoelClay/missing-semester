보너스 주제로, [정규표현식](#정규표현식)도 다룰 것입니다. 정규표현식은 코드 품질(예: 패턴과 일치하는 테스트 부분 집합을 실행하기 위해)뿐만 아니라 IDE(예: 검색 및 바꾸기)와 같은 다른 분야에도 응용되는 교차 절단 주제입니다.

이러한 도구들 중 많은 것이 언어별 기능을 할 것입니다(예: Python용 [Ruff](https://docs.astral.sh/ruff/) 린터/포매터). 어떤 경우에는 도구가 여러 언어를 지원합니다(예: [Prettier](https://prettier.io/) 코드 포매터). 하지만 개념은 거의 보편적입니다 - 어떤 프로그래밍 언어든 코드 포매터, 린터, 테스팅 라이브러리 등을 찾을 수 있습니다.

# 포매팅

코드 자동 포매터는 표면적 문법을 자동으로 정렬합니다. 이렇게 하면 더 깊고 도전적인 문제에 집중할 수 있으면서, 자동 포매팅 도구가 `'` 대 `"` 문자열 문법의 일관성, 이항 연산자 주변의 공백(`x + y` 대신 `x+y`), `import` 문들의 정렬된 순서, 그리고 과도하게 긴 라인을 방지하는 것 같은 평범한 세부 사항들을 처리합니다. 코드 포매터의 주요 이점은 코드베이스에서 일하는 모든 개발자 간에 코드 스타일을 표준화한다는 것입니다.

[Prettier](https://prettier.io/docs/configuration)와 같은 도구들은 [구성이 높이 가능합니다](https://prettier.io/docs/configuration); 프로젝트의 [버전 관리](/2026/version-control/)에 구성 파일을 체크인해야 합니다. [Black](https://github.com/psf/black)과 [gofmt](https://pkg.go.dev/cmd/gofmt)와 같은 도구들은 [자전거 헛짓](https://en.wikipedia.org/wiki/Law_of_triviality)을 줄이기 위해 제한적이거나 구성 가능성이 없습니다.

[IDE 통합](/2026/development-environment/#code-intelligence-and-language-servers)을 코드 포매터로 설정할 수 있으므로, 입력 중이거나 파일을 저장할 때 코드가 자동으로 포매팅됩니다. 프로젝트에 [EditorConfig](https://editorconfig.org/) 파일을 추가할 수도 있으며, 이는 각 파일 유형에 대한 들여쓰기 크기 같은 프로젝트 수준의 설정을 IDE에 전달합니다.

# 린팅

린터는 정적 분석(코드를 실행하지 않고 분석)을 실행하여 코드에서 안티패턴과 잠재적 문제를 찾습니다. 이 도구들은 자동 포매터보다 더 깊이 있으며, 표면적 문법을 넘어 봅니다. 분석의 깊이 수준은 도구에 따라 다릅니다.

린터는 프로젝트 수준 기반으로 구성할 수 있는 사전 설정과 함께 _규칙_의 목록을 갖추고 있습니다. 어떤 린터 규칙들은 거짓 양성을 생성하므로, 파일별 또는 라인별 기반으로 비활성화할 수 있습니다.

좋은 린터는 각 린터 규칙을 설명하는 내장된 도움말이나 문서를 가질 것입니다 - 규칙이 찾는 것, 왜 나쁜지, 그리고 코드 패턴에 대한 더 나은 대안이 무엇인지. 예를 들어, [Ruff](https://docs.astral.sh/ruff/)의 [SIM102](https://docs.astral.sh/ruff/rules/collapsible-if/) 규칙 문서를 참조하세요. 이 규칙은 Python 코드에서 불필요하게 중첩된 `if` 문을 잡아냅니다.

어떤 린터들은 문제에 플래그를 지을 뿐만 아니라 특정 문제를 자동으로 수정할 수 있습니다.

언어별 린터 외에도, [semgrep](https://github.com/semgrep/semgrep)이라는 "의미론적 grep" 도구가 유용할 수 있습니다. 이는 grep처럼 문자 수준이 아닌 AST 수준에서 작동하며 많은 언어를 지원합니다. semgrep을 사용하면 프로젝트용 커스텀 린터 규칙을 쉽게 작성할 수 있습니다. 예를 들어, Python에서 위험한 `subprocess.Popen(..., shell=True)`를 방지하고 싶다면, 다음 명령으로 그 코드 패턴을 찾을 수 있습니다:

```bash
semgrep -l python -e "subprocess.Popen(..., shell=True, ...)"
```

# 테스팅

소프트웨어 테스팅은 코드의 정확성에 대한 신뢰도를 높이기 위한 표준 기법입니다. 코드를 작성하고, 그 다음 작성한 코드를 실행하고 코드가 예상대로 작동하지 않으면 오류를 발생시키는 코드를 작성합니다.

다양한 세분화 수준에서 코드 청크들을 위한 테스트를 작성할 수 있습니다: 개별 함수를 위한 _단위 테스트_, 모듈이나 서비스 간의 상호작용을 위한 _통합 테스트_, 그리고 엔드-투-엔드 시나리오를 위한 _기능 테스트_. _테스트 주도 개발_을 할 수 있으며, 여기서 구현 코드를 작성하기 전에 먼저 테스트를 작성합니다. 코드에서 버그를 찾을 때, _회귀 테스트_를 작성하여 기능이 향후 언제든 깨질 경우 그것을 잡을 수 있습니다. Haskell의 [QuickCheck](https://hackage.haskell.org/package/QuickCheck)에서 개척된 _속성 기반 테스트_를 작성할 수 있으며, Python용 [Hypothesis](https://hypothesis.readthedocs.io/)와 같은 많은 라이브러리에서 구현되었습니다. 어떤 테스팅 접근법이 적합한지는 프로젝트에 따라 다르며, 아마도 여러 접근법의 조합을 채택할 것입니다.

프로그램이 데이터베이스나 웹 API 같은 외부 의존성을 가지고 있다면, 실제로 테스트 시 제3의 의존성과 상호작용하는 대신 테스트에서 이러한 의존성을 _모의_하는 것이 도움이 될 수 있습니다.

## 코드 커버리지

코드 커버리지는 테스트의 품질을 측정할 수 있는 메트릭입니다. 코드 커버리지는 테스트가 실행될 때 코드의 어느 라인이 실행되는지를 보여 주며, 모든 코드 경로를 커버하고 있는지 확인할 수 있습니다. 코드 커버리지 도구는 라인별 커버리지를 표시하여 테스트 작성을 안내할 수 있습니다. [Codecov](https://app.codecov.io)와 같은 서비스들은 프로젝트의 이력에 걸쳐 코드 커버리지를 추적하고 보기 위한 웹 인터페이스를 제공합니다.

모든 메트릭처럼, 코드 커버리지는 완벽하지 않습니다; 커버리지에 과도하게 가중치를 두지 말고, 고품질의 테스트 작성에 집중하세요.

# Pre-commit 훅

Git pre-commit [훅](https://git-scm.com/book/en/v2/Customizing-Git-Git-Hooks)은 [pre-commit](https://pre-commit.com/) 프레임워크로 더 쉬워지며, 모든 Git 커밋 전에 자동으로 사용자가 지정한 코드를 실행합니다. 프로젝트들은 일반적으로 pre-commit 훅을 사용하여 모든 커밋 전에 포매터와 린터를 자동으로 실행하고, 때로는 테스트도 실행하여 커밋된 코드가 프로젝트 코드 스타일과 일치하고 특정 문제들이 없음을 보장합니다.

# 지속적 통합

[GitHub Actions](https://github.com/features/actions)과 같은 지속적 통합(CI) 서비스는 코드를 푸시할 때마다(또는 모든 풀 요청에서, 또는 일정에 따라) 스크립트를 실행할 수 있습니다. 개발자들은 일반적으로 CI 서비스를 사용하여 포매터, 린터, 그리고 테스트를 포함한 코드 품질 도구를 실행합니다. 컴파일된 언어의 경우, 코드가 컴파일되도록 할 수 있습니다; 정적으로 타입이 지정된 언어의 경우, 타입이 체크되는지 확인할 수 있습니다. 새 커밋 푸시마다 CI를 실행하면 코드의 메인 버전에 도입된 오류를 잡을 수 있습니다; 풀 요청에서 실행하면 기여자 제출에 대한 문제를 잡을 수 있습니다; 일정에 따라 실행하면 외부 의존성의 문제를 잡을 수 있습니다(예: 개발자가 실수로 [semver 호환](/2026/shipping-code/#releases--versioning)으로 매김된 주요 변경 사항을 릴리스합니다).

CI 스크립트는 개발자 머신과 별도로 실행되기 때문에, 이들 스크립트에서 장기 실행 작업을 쉽게 실행할 수 있습니다. 예를 들어, 다양한 운영 체제와 프로그래밍 언어 버전에 걸쳐 테스트의 _매트릭스_를 실행하여 소프트웨어가 모든 조합에서 제대로 작동하는지 확인할 수 있습니다.

일반적으로, CI에서 실행되는 스크립트는 코드에 직접 변경을 하지 않을 것입니다: 도구들을 "수정" 모드가 아닌 "확인 전용" 모드로 실행하므로, 예를 들어 자동 포매터는 코드가 형식을 준수하지 않을 때 오류를 발생시킵니다.

저장소들은 종종 [상태 배지](https://docs.github.com/en/actions/how-tos/monitor-workflows/add-a-status-badge)를 README에 포함하며, CI 상태 및 코드 커버리지와 같은 기타 정보를 보여줍니다. 예를 들어, 아래는 Missing Semester의 현재 빌드 상태입니다.

[![Build Status](https://github.com/missing-semester/missing-semester/actions/workflows/build.yml/badge.svg)](https://github.com/missing-semester/missing-semester/actions/workflows/build.yml) [![Links Status](https://github.com/missing-semester/missing-semester/actions/workflows/links.yml/badge.svg)](https://github.com/missing-semester/missing-semester/actions/workflows/links.yml)

> 우리의 [링크 체커](https://github.com/missing-semester/missing-semester/blob/master/.github/workflows/links.yml)는 [proof-html](https://github.com/anishathalye/proof-html) GitHub Action을 사용하며, 보통 제3 웹사이트의 문제로 인해 자주 실패합니다. 그럼에도 불구하고, 그것은 우리가 많은 깨진 링크를 잡고 고치도록 도움을 주었습니다(때로는 오타로 인해, 대부분 웹사이트들이 리다이렉트를 추가하지 않고 컨텐츠를 이동하거나 웹사이트가 사라지기 때문입니다).

CI 서비스, 포매터, 린터, 그리고 테스팅 라이브러리의 세부 사항을 배우는 좋은 방법은 예제를 통한 것입니다. GitHub의 고품질 오픈 소스 프로젝트들을 찾아보세요 - 프로그래밍 언어, 도메인, 크기 및 범위 등에서 프로젝트와 더 유사할수록 더 좋습니다 - 그리고 `pyproject.toml`, `.github/workflows/`, `DEVELOPMENT.md`, 그리고 기타 관련 파일들을 검토하세요.

## 지속적 배포

지속적 배포는 CI 인프라를 활용하여 실제로 변경 사항을 _배포_합니다. 예를 들어, Missing Semester 저장소는 GitHub Pages로의 지속적 배포를 사용하므로 강의 노트를 `git push`할 때마다 사이트가 자동으로 빌드되고 배포됩니다. CI에서 애플리케이션 바이너리나 서비스용 Docker 이미지와 같은 다른 유형의 [아티팩트](/2026/shipping-code/)를 빌드할 수 있습니다.

# 명령어 러너

[just](https://github.com/casey/just)와 같은 명령어 러너는 프로젝트의 컨텍스트에서 명령어를 실행하는 작업을 단순화합니다. 프로젝트의 코드 품질 인프라를 구축할 때, 개발자들이 `uv run ruff check --fix` 같은 명령어를 암기하도록 하고 싶지 않습니다. 명령어 러너와 함께, 이것은 `just lint`로 바뀔 수 있으며, `just format`, `just typecheck` 등과 같은 유사한 호출을 가질 수 있으므로 개발자가 프로젝트를 위해 실행하고 싶은 모든 다양한 도구를 위한 호출을 할 수 있습니다.

어떤 언어별 프로젝트 또는 패키지 관리자는 이러한 기능에 대한 내장 지원을 가지고 있으며, 이는 `just`와 같은 언어별 도구를 사용할 필요가 없다는 의미입니다. 예를 들어, [npm](https://nodejs.org/en/learn/getting-started/an-introduction-to-the-npm-package-manager)(Node.js)용 `package.json`의 `scripts` 섹션과 [Hatch](https://hatch.pypa.io/)(Python)용 `pyproject.toml`의 `tool.hatch.envs.*.scripts` 섹션은 이 기능을 지원합니다.

# 정규표현식

_정규표현식_은 보통 "regex"로 축약되며, 문자열들의 집합을 나타내는 데 사용되는 언어입니다. 정규표현식 패턴은 명령어 라인 도구와 IDE와 같은 다양한 컨텍스트에서 패턴 매칭에 일반적으로 사용됩니다. 예를 들어, [ag](https://github.com/ggreer/the_silver_searcher)는 코드베이스 전체 검색을 위해 정규표현식 패턴을 지원합니다(예: `ag "import .* as .*"`는 Python에서 모든 이름을 바꾼 import를 찾을 것입니다), 그리고 [go test](https://pkg.go.dev/cmd/go#hdr-Test_packages)는 테스트 부분 집합을 선택하기 위해 `-run [regexp]` 옵션을 지원합니다. 더욱이, 프로그래밍 언어들은 정규표현식 매칭에 대한 내장 지원이나 제3자 라이브러리를 가지고 있어서, 패턴 매칭, 검증, 그리고 파싱과 같은 기능에 정규표현식을 사용할 수 있습니다.

직관을 구축하기 위해, 아래에는 정규표현식 패턴들의 몇 가지 예들이 있습니다. 이 강의에서는 [Python 정규표현식 문법](https://docs.python.org/3/library/re.html)을 사용합니다. 정규표현식의 많은 풍미들이 있으며, 더 정교한 기능들 특히 그들 간에 약간의 변형이 있습니다. [regex101](https://regex101.com/)과 같은 온라인 정규표현식 테스터를 사용하여 정규표현식을 개발하고 디버그할 수 있습니다.

- `abc` --- 문자 "abc"를 매칭합니다.
- `missing|semester` --- 문자 "missing" 또는 문자 "semester"를 매칭합니다.
- `\d{4}-\d{2}-\d{2}` --- "2026-01-14"와 같은 YYYY-MM-DD 형식의 날짜를 매칭합니다. 문자가 4개 숫자, 대시, 2개 숫자, 대시, 그리고 2개 숫자로 구성되어 있음을 보장하는 것 외에는, 이것은 날짜를 검증하지 않으므로 "2026-01-99"도 이 정규표현식 패턴과 매칭됩니다.
- `.+@.+` --- 이메일 주소들을 매칭합니다. 어떤 텍스트, 그 다음 "@", 그리고 그 다음 더 많은 텍스트를 포함하는 문자들입니다. 이것은 기본 검증만 수행하고 "nonsense@@@email" 같은 문자들과 매칭합니다. 거짓 양성이나 거짓 음성이 없이 이메일 주소들과 매칭하는 정규표현식이 [존재](https://pdw.ex-parrot.com/Mail-RFC822-Address.html)하지만 비실용적입니다.

## 정규표현식 문법

[이 문서](https://docs.python.org/3/library/re.html#regular-expression-syntax)에서 정규표현식 문법에 대한 포괄적인 가이드를 찾을 수 있습니다(또는 온라인에서 이용 가능한 다른 많은 리소스들). 다음은 몇 가지 기본 빌딩 블록입니다:

- `abc` --- 문자들이 특별한 의미를 가지지 않을 때 문자 문자를 매칭합니다(이 예에서는 "abc").
- `.` --- 모든 단일 문자를 매칭합니다.
- `[abc]` --- 괄호에 포함된 단일 문자를 매칭합니다(이 예에서는 "a", "b", 또는 "c").
- `[^abc]` --- 괄호에 포함된 것을 제외한 단일 문자를 매칭합니다(예: "d").
- `[a-f]` --- 괄호에 표시된 범위에 포함된 단일 문자를 매칭합니다(예: "c", 하지만 "q" 아님).
- `a|b` --- 두 패턴 중 하나를 매칭합니다(예: "a" 또는 "b").
- `\d` --- 모든 숫자 문자를 매칭합니다(예: "3").
- `\w` --- 모든 단어 문자를 매칭합니다(예: "x").
- `\b` --- 모든 단어 _경계_를 매칭합니다(예: "missing semester" 문자에서, "m" 바로 앞에, "g" 바로 뒤에, "s" 바로 앞에, 그리고 "r" 바로 뒤에 매칭합니다).
- `(...)` --- 패턴의 그룹을 매칭합니다.
- `...?` --- 패턴의 0개 또는 1개를 매칭합니다. 예를 들어 `words?`는 "word" 또는 "words"를 매칭합니다.
- `...*` --- 패턴의 임의의 개수를 매칭합니다. 예를 들어 `.*`는 모든 문자의 임의의 개수를 매칭합니다.
- `...+` --- 패턴의 하나 이상을 매칭합니다. 예를 들어 `\d+`는 숫자의 0이 아닌 개수를 매칭합니다.
- `...{N}` --- 패턴의 정확히 N개를 매칭합니다. 예를 들어 `\d{4}`는 4개의 숫자를 위한 것입니다.
- `\.` --- 문자 "."를 매칭합니다.
- `\\` --- 문자 "\\"를 매칭합니다.
- `^` --- 라인의 시작을 매칭합니다.
- `$` --- 라인의 끝을 매칭합니다.

## 캡처 그룹과 참조

정규표현식 그룹 `(...)`을 사용하는 경우, 추출 또는 검색 및 바꾸기 목적으로 매칭의 부분을 참조할 수 있습니다. 예를 들어, YYYY-MM-DD 스타일 날짜에서 월만 추출하려면, 다음 Python 코드를 사용할 수 있습니다:

```python
>>> import re
>>> re.match(r"\d{4}-(\d{2})-\d{2}", "2026-01-14").group(1)
'01'
```

텍스트 에디터에서, 정규표현식 그룹을 참조하여 패턴을 바꿀 수 있습니다. 문법은 IDE들 간에 다를 수 있습니다. 예를 들어, VS Code에서는 `$1`, `$2` 등의 변수를 사용할 수 있으며, Vim에서는 `\1`, `\2` 등을 사용할 수 있습니다.

## 한계

[정규 언어들](https://en.wikipedia.org/wiki/Regular_language)은 강력하지만 제한적입니다; 표준 정규표현식으로 표현할 수 없는 문자열의 클래스들이 있습니다(예: {a^n b^n \| n ≥ 0}의 문자열 집합, "a"의 개수 뒤에 같은 개수의 "b"들을 매칭하는 정규표현식을 작성하는 것은 [불가능](https://en.wikipedia.org/wiki/Pumping_lemma_for_regular_languages)합니다; 더 실용적으로, HTML과 같은 언어들은 정규 언어가 아닙니다). 실제로, 최신 정규표현식 엔진들은 lookahead와 역참조 같은 기능을 지원하여 정규 언어를 넘어 지원을 확장합니다. 그들은 실제로 매우 유용하지만, 여전히 그들의 표현 능력에는 한계가 있다는 것을 아는 것이 중요합니다. 더 정교한 언어를 위해, 더 능력이 있는 파서의 유형에 도달해야 할 것입니다(예를 들어, [pyparsing](https://github.com/pyparsing/pyparsing)을 참조하세요. 이것은 [PEG](https://en.wikipedia.org/wiki/Parsing_expression_grammar) 파서입니다).

## 정규표현식 배우기

우리는 기본 사항을 배우고(이 강의에서 다룬 것), 그 다음 필요할 때 정규표현식 참조를 살펴보는 것을 추천합니다. 언어 전체를 암기하기보다는요.

대화형 AI 도구들은 정규표현식 패턴을 생성하는 데 효과적일 수 있습니다. 예를 들어, 다음 쿼리로 당신이 좋아하는 LLM에 프롬프트를 시도해 보세요:

```
Write a Python-style regex pattern that matches the requested path from log lines from Nginx. Here is an example log line:

169.254.1.1 - - [09/Jan/2026:21:28:51 +0000] "GET /feed.xml HTTP/2.0" 200 2995 "-" "python-requests/2.32.3"
```
